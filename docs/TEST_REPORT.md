# ANTARES Android test report

Target device is the Samsung Galaxy A14 5G SM-A146U, Android 15. Hosted Android tests run on an x86_64 API 35 emulator. The APK includes the arm64-v8a ABI for the Galaxy A14. The APK is a development candidate. Physical-device and production release gates remain open.

## Recovery and authority

The existing ANTARES repository is the authoritative codebase. The audit recovered native Android prototypes 0.1 and 0.2, the Python v2.x workstations, Phases 2 and 3 through 3.2.1, staged 10C/10D tools, G-Core fixtures, revision audits, the Phase 1.3 browser face engine, and the original project specifications. The separate reconstruction release-candidate checklist marked forensic chirality as unimplemented. Existing source photographs and legacy source archives were preserved.

The recovered facial model matched the original recorded SHA-256 `64184e229b263107bc2b804c6625db1341ff2bb731874b0bcc2fe6544e0bc9ff`. A historical landmark export recorded 62 detections and six no-face results. Five same-named candidate source files differed in bytes and dimensions. A desktop probe reproduced the face/no-face outcome on all five and measured a mean 2D difference between 0.00079 and 0.00336 for detections. Exact historical parity and complete migration still require the matching original source set and any phone-only project database. The public test fixture contains no private photographs.

## Defects and regression strategy

- Previous Android CI setup failed before compile. The replacement builds with a pinned Gradle and SDK, checks the packaged manifest and signature, and installs the exact artifact on API 35.
- The original prototype overwrote singleton files and recompressed its local original copy. Durable subject records, SHA-256-keyed private source copies and separate derivatives preserve source data.
- The first JSON acceptance run used a MediaStore row without an empty backing file. The fixture now creates a real destination and rechecks exports without weakening readback.
- Full-frame facial detection missed small faces. Overlapping windows recovered 2/2 and 16/16 candidates in controlled fixtures. Seed 381459 checks recovered both subjects in reduced-scale, dim, tilted, and partially obscured desktop samples. A heavily obscured subject was missed and remains a real-world qualification gate.
- Job rescheduling could be skipped when Android still listed a terminating job. The schedule now replaces the stale request. Twelve idle handoffs were included in the suite.
- The initial interactive adapter assumed two mask planes. The model returned one foreground confidence map. The adapter now handles that contract and tests real transparent and opaque mask pixels.
- Android then exposed that the interactive inference object could recycle a cached source bitmap. The detector now receives a disposable bitmap copy and the original crop remains available for compositing. The real-model cutout regression exercises this ownership boundary.

## Installation and device acceptance

Extract `ANTARES-development.apk` and `SHA256SUMS.txt` from the CI artifact. Install the APK from Android Files, launch ANTARES, and select or create an active SUBJECT. Add test photos through Photos and files. Confirm an intended subject and run the chosen workflow. In Photos and files, select the exact result and use Save As JSON, CSV or PNG. For physical acceptance, choose separate folders for JSON and CSV, repeat with an SD-card folder when available, and reopen the resulting files.

For isolation and compositing, choose a two-person photo, confirm one region, refine the cutout and inspect all five backgrounds before rendering. Reopen the completed mask, change backgrounds without rerunning isolation, and save a second result. Back up the SUBJECT, restore it under a new name, and verify that scans, outputs and masks stay associated with the restored subject. Test restart, unexpected process termination, low storage, long sessions, and memory usage separately.

A different existing signing certificate can prevent an update and requires a separately planned migration. Existing data should be backed up before changing installations. Physical SM-A146U acceptance, large stress scenarios, forensic implementation and production signing remain open.
